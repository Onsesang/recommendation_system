# Experiment 24 — Adaptive tactile-aware recommendation

Generated by `scripts/09_report.py` from `results/`.

---

## 1. The question this experiment actually asks

Not *"is tactile useless for recommendation?"* — experiments 16b, 17b, 19 and 20
already failed four times. The question is narrower and fairer:

> **Was the problem that tactile was added to every user and item in the same
> fixed proportion?**

So every method here replaces the global `alpha` with something conditional,
learnable, user-specific, item-specific or confidence-aware, and each is measured
against the same backbone.

The pre-existing audit is in `EXP16_17_AUDIT.md`.

## 3. Candidate recall — the constraint everything else sits inside

| split | sasrec@100 | sasrec@300 | sasrec@500 | tactile@100 | tactile@300 | tactile@500 | tactile_std@100 | tactile_std@300 | tactile_std@500 | union_tactile@500+500 | union_tactile_std@500+500 | full_catalog_recall@10 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| validation | 0.020773 | 0.031430 | 0.038083 | 0.000339 | 0.000950 | 0.001358 | 0.000611 | 0.001222 | 0.002240 | 0.039373 | 0.040052 | 0.005499 |
| test | 0.019172 | 0.028775 | 0.035177 | 0.000267 | 0.000634 | 0.001100 | 0.000300 | 0.001134 | 0.001834 | 0.036211 | 0.036878 | 0.005768 |

SASRec finds the held-out item inside its top 500 for only **0.0352**
of test users. **~96.5 % of the time the right answer is not in the candidate set
at all**, so no reranker — fixed, gated or learned — can reach it. Every reranking
result below is bounded by that.

### Is that a bug? No — and here is the evidence

`scripts/13_retrieval_diagnostic.py` (output in
`results/retrieval_bottleneck_diagnostic.json`) runs checks that would each fail
loudly on a broken pipeline, then quantifies the cause.

**Correctness checks, all passing:**

| check | result |
|---|---|
| minimum history length | 3 |
| cohort definition (history >= 3) holds for every user | True |
| padded matrix non-zeros match history length | True |
| right-aligned, last slot is the most recent item | True |
| target leaked into the history | **0** cases |
| trained checkpoint vs random init, Recall@500 | 0.036007 vs 0.001000 (**36x**) |

The checkpoint is genuinely trained and correctly loaded, the histories are built
and aligned correctly, and nothing leaks.

**The cause is the data, in three compounding layers:**

| | |
|---|---:|
| catalog items that never appear in training | **86.7%** (716,384 of 825,869) |
| test targets that are among those unseen items | **71.5%** |
| ceiling on Recall for *any* collaborative model | **0.2849** |
| mean training history, users who have any | 2.05 items (76,755 users) |
| mean history of the evaluated cohort | 4.69 items |

An item never seen in training keeps a randomly-initialised embedding, so it cannot
enter a top-500 of 825,869. The diagnostic confirms this exactly: **Recall@500 on
cold targets is 0.000000**.
SASRec reaches 0.0360 of an achievable
0.2849 — about an eighth of the ceiling.

### The more uncomfortable finding: SASRec does not beat popularity at *retrieval*

| | all test users | targets seen in training |
|---|---:|---:|
| SASRec (trained) | 0.036007 | 0.120724 |
| **Popularity top-500** | **0.036607** | **0.122736** |

A static popularity list retrieves marginally *more* of the held-out items than the
trained sequential model, and **47.9%
of SASRec's top-500 is literally the popularity top-500**. With a mean training
history of 2.05 items and
87% of the catalog unseen, the
model has almost nothing to personalise *retrieval* with and collapses toward
popularity.

It does still beat popularity on **ranking** (exp17b: NDCG@10 0.00349 vs 0.00281),
so what personalisation it learns shows up in ordering the few candidates it
surfaces, not in surfacing better ones.

**Consequence.** The tactile reranking question is being asked inside a candidate
set that is ~96.5 % wrong and roughly half popularity. That is not a tuning failure
to be fixed by a better alpha or gate; it is a property of Amazon Reviews'23
`Amazon_Fashion` under the official 0core leave-last-out protocol with the full
825k catalog retained. Published sequential-recommendation numbers on *k-core
filtered* Clothing subsets are not comparable to these, and this report does not
compare them.

## 4. R1 — fixed alpha, and a diagnostic that rules out an implementation excuse

The audit noticed that exp17b's rule,
`final = where(valid, bp + a·(tp − bp), bp)`, moves only those candidates that
*have* a tactile vector, leaving the rest on the original scale — which would
re-order items by tactile **availability** rather than tactile **fit**. If that
were the cause, fixed alpha would deserve a retrial rather than a verdict.

So R1b applies the same alpha to **every** candidate on one common scale.

| alpha | R1_exp17_rule | R1b_common_scale |
|---|---|---|
| 0.00000000 | 0.00300162 | 0.00300162 |
| 0.05000000 | 0.00257567 | 0.00257469 |
| 0.10000000 | 0.00229521 | 0.00229521 |
| 0.15000000 | 0.00217661 | 0.00217661 |
| 0.20000000 | 0.00201573 | 0.00201671 |
| 0.25000000 | 0.00181401 | 0.00181401 |
| 0.30000000 | 0.00166656 | 0.00166656 |
| 0.40000000 | 0.00143683 | 0.00143683 |
| 0.50000000 | 0.00121490 | 0.00121490 |
| 0.60000000 | 0.00102914 | 0.00102914 |
| 0.70000000 | 0.00088964 | 0.00088964 |
| 0.80000000 | 0.00084289 | 0.00084370 |
| 0.90000000 | 0.00068002 | 0.00068002 |
| 1.00000000 | 0.00049940 | 0.00049940 |

The two curves are indistinguishable and both fall monotonically. Validation
selects **alpha = 0** for both.

> **The audit's hypothesis is refuted.** The combination rule was not the problem.
> Fixed alpha fails because the tactile term carries no useful ordering
> information, not because of how it was mixed in.

## 5. R2 — learned per-(user, item) gate

`g(u,i) ∈ [0,1]` from a small MLP over: backbone score percentile, tactile cosine
to the user's past-only profile, tactile percentile, tactile availability,
popularity, category match, history length, user tactile consistency, profile
support, and predictor confidence.

Two design decisions make the result interpretable rather than an artefact:

1. the head is initialised so that at step 0 it reproduces the R0 ordering, so
   **R0 lies inside the hypothesis space**;
2. the epoch is chosen on **validation**, epoch 0 included — so a trained gate is
   only reported as better if it actually is, on data it was not fitted on.

### The gate initialisation sweep is the informative result

| init_bias | lr | validation_NDCG@10 | gate_mean | gate_std | across_user_std |
|---|---|---|---|---|---|
| -6.00000000 | 0.00100000 | 0.00303138 | 0.00250357 | 0.00000099 | 0.00000019 |
| -6.00000000 | 0.01000000 | 0.00298127 | 0.00247263 | 0.00000001 | 0.00000000 |
| -2.00000000 | 0.00100000 | 0.00226639 | 0.11920211 | 0.00000080 | 0.00000001 |
| -2.00000000 | 0.01000000 | 0.00226639 | 0.11920211 | 0.00000080 | 0.00000001 |
| 0.00000000 | 0.00100000 | 0.00174169 | 0.31109494 | 0.02322011 | 0.00423837 |
| 0.00000000 | 0.01000000 | 0.00247650 | 0.47097757 | 0.29394084 | 0.02166266 |

Read this table carefully:

- The configuration that produces a **genuinely dispersed** gate (std ≈ 0.29, init 0.0,
  lr 0.01) scores **worse** than the baseline.
- The configuration validation **selects** has gate mean ≈ 0.0025 and std ≈ 1.7e-06 —
  a constant, and a constant very close to zero. The "learned adaptive gate" wins
  by **switching tactile off**.
- Validation NDCG@10 falls monotonically as the gate's magnitude rises.

> This is the direct answer to *"maybe the weight just shouldn't be global"*.
> Given a weight free to vary per user and per item, validation drives it to zero,
> and forcing it to vary makes things worse.

Selected setting: `{'init_bias': -6.0, 'lr': 0.001, 'validation_NDCG@10': 0.0030313775015218952, 'gate_mean': 0.0025035683065652847, 'gate_std': 9.944723160515423e-07, 'gate_p05': 0.002502089599147439, 'gate_p95': 0.0025053308345377445, 'across_user_std': 1.873750647973793e-07}`.

## 6. R7 — hybrid candidate generation + learned reranker

SASRec top-500 ∪ tactile-ANN top-500, rescored by a learned ranker. Its head is
zero-initialised so that before training it reproduces the backbone ordering
restricted to the union.

**Candidate recall and final ranking are reported separately**, as the task requires:

| | validation | test |
|---|---:|---:|
| SASRec Recall@500 | 0.038083 | 0.035177 |
| union Recall@500+500 | 0.040052 | 0.036878 |
| **recall gained** | **+0.001969** | **+0.001701** |
| NDCG@10 gained | 0.00000000 | 0.00000000 |

The tactile arm **does** add candidates the backbone missed — and **none of them
reach the top 10**. Validation selected epoch 0 for the reranker, i.e. the
untrained no-op: the learned ranker never beat the backbone's own ordering.

The autonomous follow-up **A24-1** (`AUTONOMOUS_EXPERIMENTS.md`) tested whether the
weak tactile arm was an artifact of the similarity measure. Standardising each
tactile dimension before the cosine improved the tactile arm by 1.65× — the
mechanism was diagnosed correctly — but from 0.00136 to 0.00224, against a
pre-registered success bar of 0.010. **H rejected.** A 14-dimensional,
largely positively-correlated tactile vector cannot index an 825k catalog.

### R5 looked like the project's first recommendation win. The control says otherwise.

R5 mines hard negatives that are same-category, similar-popularity but
tactile-distant from the positive. It beats R0 decisively on both splits:

| | validation | test |
|---|---:|---:|
| R0 (random negatives) | 0.00212398 | 0.00179340 |
| R5, real tactile table | 0.00270890 | 0.00271676 |
| **R5, tactile table permuted** | 0.00260951 | 0.00272138 |

The control keeps the mining procedure byte-identical and only permutes the tactile
table, so the sampler still picks "distant" items -- in an arbitrary space.

| contrast | delta | 95 % CI | verdict |
|---|---:|---|---|
| real − shuffled, validation | +0.00009939 | [-0.00047240, +0.00073466] | not significant |
| real − shuffled, test | -0.00000462 | [-0.00041189, +0.00038502] | not significant |

**Permuting the tactile vectors changes nothing** -- on test the permuted arm is
marginally *higher*. So R5's gain is real but it belongs to **hard-negative mining**,
not to tactile information. Any representation that separates same-category items
would plausibly do the same job. Reporting R5 as "tactile finally helps
recommendation" would have been a false positive, and this control is the only
reason it is not in this report as one.

This is the exp20 `aligned − shuffle ≈ 0` result reproduced in a fifth independent
design.

## 9. How this differs from experiments 16b / 17b

exp16b and exp17b reported `delta = 0, CI = [0, 0]`, but that was **not** a test of
whether tactile helps: validation had selected `alpha = 0`, switching the tactile
term off before test was ever scored. That objection does not apply here:

| objection to the old result | how this experiment removes it |
|---|---|
| "alpha was global, of course it failed" | R2 learns `g(u,i)` per pair, free over [0,1]; validation still drives it to ≈0, and forcing dispersion is worse |
| "the combination rule was broken" | R1b uses one common scale for all candidates; identical alpha curve, still selects 0 |
| "the reranker was not learned" | R7 fits a learning-to-rank head; validation selects the untrained no-op over it |
| "candidates never contained the answer" | quantified: union adds +0.0017 recall and +0.0000 NDCG@10 |
| "the gate was never given a chance to start from a useful value" | swept three initialisations spanning g ≈ 0.002 to 0.47 |

## 10. Conclusion

1. **Making the tactile weight adaptive does not rescue it.** A per-(user, item)
   learned gate, selected on validation, collapses to a near-zero constant; when
   forced to vary it performs worse than no tactile at all.
2. **The combination rule was not the culprit** — the audit's own hypothesis, tested
   and refuted by R1b.
3. **Tactile candidate generation raises recall slightly and ranking not at all.**
4. **No user subgroup benefits**, including the ones defined to be most favourable.
5. The dominant constraint is retrieval: the target is outside the top 500 for
   ~96.5 % of users. Any tactile reranking claim on this dataset is bounded by that.

Taken with experiment 23 — where the same Last2 predictor produced a large,
significant retrieval gain that survived removing the category shortcut — the
coherent reading is that **the tactile signal is real but belongs to explicit
tactile search, not to implicit next-item prediction.** Amazon interactions are
simply not labels of tactile satisfaction.

---

## 11. Limitations

1. **Locked post-hoc exploratory, not confirmatory.** exp16b already opened this
   test split; no claim here is confirmatory.
2. Tactile vectors are Last2 predictions over catalog images — predictions about
   pseudo-labels, two steps from any measured tactile property.
3. R2 and R7 fit on ~2,000 users, the only ones whose target falls inside the
   candidate set. That is a real limit on what a learned head can learn, and it is
   itself a consequence of the recall bottleneck.
4. The shared A100 belonged to another user's job for the first hours; our GPU use
   contributed to an OOM that killed one of their processes, after which we stayed
   off the device entirely until it was free.
5. `history ≥ 3` covers only 1.5 % of the official test population.
